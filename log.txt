1. PROBLEM STATEMENT SUMMARY
================================================================================

Northstar Shop (fictional e-commerce company) receives deletion requests from
customers under GDPR Article 17, CCPA, and internal privacy policies.

INPUT  : dataset/deletion_requests.csv — 518 cases
         Each row: case_id, email, request_text, requested_at, audit_at

OUTPUT : output.csv — one row per case
         Columns: case_id, deletion_status, steps_json

DELETION STATUS VALUES:
  NOT_APPLICABLE  — Customer did not request deletion (data export, question, etc.)
                    steps_json = []

  COMPLETE        — All required deletions confirmed done at audit_at
                    steps_json contains ONLY VERIFICATION steps, each with a
                    real evidence_id (file_id / activity_id / audit_id)

  INCOMPLETE      — Gaps found: records still present, PII exposed, active
                    data flows, or restore risks exist
                    steps_json contains FINDING (evidence_id filled) +
                    REMEDIATION (evidence_id = "") + VERIFICATION (evidence_id = "")

STEP SCHEMA:
  { step_no, phase, system_id, resource_id, operation, state, evidence_id }

ALLOWED (phase, operation, state) COMBINATIONS:
  FINDING:
    REPORT_REMAINING_RECORD / PRESENT
    REPORT_EXPOSED_PII       / PRESENT
    REPORT_ACTIVE_DATA_FLOW  / ACTIVE
    REPORT_RESTORE_RISK      / ACTIVE

  REMEDIATION:
    DISABLE_DATA_FLOW  / DISABLED
    BLOCK_RESTORE      / BLOCKED
    DELETE_RECORD      / ABSENT
    REDACT_RECORD      / REDACTED
    ANONYMIZE_RECORD   / ANONYMIZED

  VERIFICATION:
    VERIFY_RECORD_ABSENT       / ABSENT
    VERIFY_RECORD_PRESENT      / PRESENT
    VERIFY_RECORD_REDACTED     / REDACTED
    VERIFY_RECORD_ANONYMIZED   / ANONYMIZED
    VERIFY_DATA_FLOW_DISABLED  / DISABLED
    VERIFY_RESTORE_BLOCKED     / BLOCKED

STEP ORDERING RULES:
  1. Phase order: FINDING → REMEDIATION → VERIFICATION
  2. Within phase: operation order (per table above)
  3. Then: system_id ascending
  4. Then: resource_id ascending
  5. step_no starts at 1 and is consecutive

TOMBSTONE RULE:
  A tombstone record may retain user_id ONLY.
  It must NOT contain: name, email, phone, email_hash, full_name,
                       display_name, email_address

RETAINED RECORDS:
  Some systems require records to be kept (e.g., invoices for 7 years).
  Even retained records must not expose forbidden PII unless explicitly
  listed in permitted_identifiers in deletion_rules.csv.

2. ARCHITECTURE OVERVIEW
================================================================================

ghost-audit/ uses a deterministic multi-stage pipeline with LLM only as a
fallback for genuinely ambiguous cases.

  PIPELINE (per case):
  ┌─────────────────┐
  │ load_data.py    │  Load & normalise all 8 CSVs into DataBundle
  └────────┬────────┘
           │
  ┌────────▼────────┐
  │ intent.py       │  Stage-1: regex keyword rules (deterministic)
  │                 │  Stage-2: LLM via llm.py (only if confidence < 0.80
  │                 │           or conflicting signals)
  └────────┬────────┘
           │ NOT_APPLICABLE → output []
           │
  ┌────────▼────────┐
  │ identity.py     │  Resolve email → user_id + all identifier variants
  │                 │  (current email, historical emails, phone, name,
  │                 │   MD5/SHA-256/SHA-1 hashes, plus-address variants)
  └────────┬────────┘
           │
  ┌────────▼────────┐
  │ evidence.py     │  Search all evidence files for any identifier match
  │                 │  SQLite / JSON / CSV / PDF / image / txt / log
  │                 │  OCR fallback; vision LLM for low-confidence images
  └────────┬────────┘
           │
  ┌────────▼────────┐
  │ state.py        │  Replay system_activity.csv chronologically up to audit_at
  │                 │  Cross-check DELETE claims with evidence
  │                 │  Detect SYNC/BACKUP/RESTORE risks
  └────────┬────────┘
           │
  ┌────────▼────────┐
  │ rules.py        │  Apply deletion_rules.csv to each resource state
  │                 │  Generate Gap records (REMAINING_RECORD, EXPOSED_PII,
  │                 │  ACTIVE_DATA_FLOW, RESTORE_RISK)
  │                 │  Call decide_status() → COMPLETE / INCOMPLETE
  └────────┬────────┘
           │
  ┌────────▼────────┐
  │ steps.py        │  Build ordered step list from gaps + state_report
  │                 │  De-duplicate, sort, renumber step_no
  └────────┬────────┘
           │
  ┌────────▼────────┐
  │ validate.py     │  12-rule schema + logic validation
  └────────┬────────┘
           │
         output.csv

KEY DESIGN PRINCIPLE:
  Deterministic Python for everything verifiable.
  LLM only for:
    (a) Intent classification when regex confidence < 0.80
    (b) Evidence extraction from PDFs/images with unstructured free text
    (c) Vision extraction from low-confidence OCR images
  All LLM calls are cached by SHA-256(model + system + prompt).
  Every LLM call is logged to evaluation/llm_calls.jsonl.

CONCURRENCY:
  main.py uses ThreadPoolExecutor (default 4 workers).
  Per-case errors fall back to INCOMPLETE with empty steps rather than
  crashing the whole run.

    .current_identifiers      {emails, phones, names, email_hashes}
    .historical_identifiers   same, from audit_log
    .source_ids               list of audit_id / activity_id as evidence
    .ambiguous                bool (True if email reassigned between users)
    .ambiguity_note           explanation string
    .all_identifiers          flat set of all PII tokens to search for
  Steps:
    1. Exact match in identities.csv (after plus-address normalisation)
    2. Enrich from audit_log (catches historical emails, old names)
    3. Detect reassignment ambiguity (same email, different user_id over time)
    4. Compute MD5 / SHA-256 / SHA-1 hashes for each known email
  Plus-address handling: user+tag@domain → user@domain before matching

── src/evidence.py ─────────────────────────────────────────────────────────────
  Input : IdentityBundle, evidence_manifest df, evidence_dir path
  Output: list[EvidenceMatch]
    .file_id, .system_id, .resource_id, .field, .matched_value, .raw_snippet
  File type handlers:
    .db / .sqlite  → in-memory sqlite3; enumerate all tables; search text cols
    .json          → parse + recursive json.dumps; text search
    .jsonl         → line-by-line parse; text search
    .csv           → pandas read; search all str columns
    .pdf           → pdfplumber text extraction; OCR fallback if empty
    .png/.jpg/...  → pytesseract OCR; vision LLM if avg_conf < 60
    .txt/.log/.md  → plain text search
  Primary key inference: looks for "id", "<table>_id", "user_id", "record_id"
  Disk cache: .cache/evidence/<filename>.txt (parsed text, reused across runs)
  Unknown extensions: logged as WARNING, return [] (never raise)

── src/state.py ────────────────────────────────────────────────────────────────
  Input : IdentityBundle, audit_at, activity df, evidence_matches list
  Output: StateReport
    .resource_states  dict[(system_id, resource_id)] → ResourceState
    .active_flows     list[ActiveFlow]   (SYNC/IMPORT still running at audit_at)
    .restore_risks    list[RestoreRisk]  (BACKUP snapshots that can restore data)
    .timeline         str (debug trace of all replayed events)
  Replay logic:
    - Events filtered to: user_id match OR any identifier in row; ts <= audit_at
    - DELETE/PURGE → mark ABSENT, but cross-check with evidence:
        if evidence still shows the identifier → override to PRESENT
    - SYNC/IMPORT → if job active at audit_at OR ran after a DELETE → ACTIVE_FLOW
    - BACKUP/SNAPSHOT → always add RestoreRisk
    - RESTORE → mark PRESENT (data came back)
    - DISABLE/DEACTIVATE → remove from active_flows list
    - REDACT/ANONYMIZE → mark REDACTED / ANONYMIZED
    - CREATE/UPDATE → mark PRESENT (if not already present)
  Evidence fallback: if resource found in evidence but not in activity → PRESENT

── src/rules.py ────────────────────────────────────────────────────────────────
  required_treatment(system_id, resource_type, rules_df):
    Looks up deletion_rules.csv; normalises column names
    Returns: {action, permitted_identifiers, retention_days, tombstone_allowed}
    Fallback: wildcard/default rows; default action = DELETE

  evaluate(state_report, evidence_matches, identity, rules_df):
    For each (system_id, resource_id) in state_report:
      - Infer resource_type from name heuristics
      - Look up required treatment
      - RETAIN_AS_IS → add to retained list; check for forbidden PII → EXPOSED_PII gap
      - DELETE + state PRESENT → REMAINING_RECORD gap
      - REDACT/ANONYMIZE + state PRESENT → check for exposed PII → EXPOSED_PII gap
      - tombstone_allowed + state PRESENT → check forbidden fields → EXPOSED_PII gap
    For each active_flow  → ACTIVE_DATA_FLOW gap
    For each restore_risk → RESTORE_RISK gap
    Returns EvaluationResult(gaps, retained, deletion_status)

  decide_status(intent, eval_result):
    NOT is_deletion         → NOT_APPLICABLE
    any gap exists          → INCOMPLETE
    no gaps                 → COMPLETE

  Tombstone forbidden fields: name, email, phone, email_hash,
                               full_name, display_name, email_address
  Tombstone permitted fields: user_id (only)

── src/steps.py ────────────────────────────────────────────────────────────────
  build_steps(deletion_status, gaps, retained, state_report):

  Gap → Step mapping:

    EXPOSED_PII_REDACT → REPORT_EXPOSED_PII / REDACT_RECORD / VERIFY_RECORD_REDACTED
    EXPOSED_PII_ANON   → REPORT_EXPOSED_PII / ANONYMIZE_RECORD / VERIFY_RECORD_ANONYMIZED
    ACTIVE_DATA_FLOW   → REPORT_ACTIVE_DATA_FLOW / DISABLE_DATA_FLOW / VERIFY_DATA_FLOW_DISABLED
    RESTORE_RISK       → REPORT_RESTORE_RISK / BLOCK_RESTORE / VERIFY_RESTORE_BLOCKED
  De-duplication: same (phase, system_id, resource_id, operation) removed
  Sort key: (_PHASE_ORDER, _OP_ORDER, system_id, resource_id)
  Renumber: step_no = 1, 2, 3, ...

5. DELETION RULES INTERPRETATION
================================================================================

Rule 1  — DEFAULT (*): customer_record
  Action: DELETE | Tombstone: No
  All customer records deleted by default unless overridden by system-specific rule.

Rule 2  — CRM: customer_record
  Action: DELETE | Tombstone: YES (permitted)
  CRM may keep a tombstone but MUST remove name, email, phone, email_hash.
  Only user_id may remain.

Rule 3  — ORDER_MGMT: order_record
  Action: RETAIN_AS_IS | Permitted: order_id, amount | Retention: 2555 days (7 years)
  Financial compliance. PII fields beyond order_id/amount must be redacted.

Rule 4  — ORDER_MGMT: invoice
  Action: RETAIN_AS_IS | Permitted: order_id, amount | Retention: 2555 days
  Tax/accounting compliance — same as order records.

Rule 5  — BILLING: invoice
  Action: RETAIN_AS_IS | Permitted: order_id, amount | Retention: 2555 days
  Legal/tax retention requirement.

Rule 6  — ANALYTICS: analytics_event
  Action: ANONYMIZE | Permitted: event_id, ts | Retention: 365 days
  Event data anonymized; statistical value retained.

Rule 7  — ANALYTICS: user_profile
  Action: DELETE | Tombstone: No
  Full deletion of analytics user profiles.

Rule 8  — EMAIL_SVC: email_log
  Action: DELETE | Tombstone: No
  Email logs fully deleted on request.

Rule 9  — SUPPORT: support_ticket
  Action: REDACT | Permitted: ticket_id | Retention: 730 days (2 years)
  Support tickets redacted; ticket_id retained for operational continuity.

Rule 10 — BACKUP_SYS: backup_snapshot
  Action: DELETE | Tombstone: No
  Backup snapshots containing user data must be purged.

Rule 11 — SEARCH_IDX: search_index
  Action: DELETE | Tombstone: No
  Search index entries removed.

Rule 12 — DATA_WAREHOUSE: analytics_event
  Action: ANONYMIZE | Permitted: event_id | Retention: 730 days
  DW event data anonymized.

Rule 13 — DATA_WAREHOUSE: user_profile
  Action: DELETE | Tombstone: No
  DW user profiles deleted.

Rule 14 — NOTIFICATION_SVC: notification_pref
  Action: DELETE | Tombstone: No
  Notification preferences deleted.

SUMMARY:
  RETAIN_AS_IS : ORDER_MGMT orders/invoices, BILLING invoices (financial law)
  ANONYMIZE    : ANALYTICS events, DATA_WAREHOUSE events
  REDACT       : SUPPORT tickets (keep ticket_id only)
  DELETE       : Everything else

7. DESIGN DECISIONS & RATIONALE
================================================================================

DECISION 1: Two-Stage Intent Classifier
  Problem: LLM calls are slow and costly at scale (518 cases).
  Solution: Stage-1 regex (deterministic, <1ms) handles ~90% of cases.
            Stage-2 LLM only for ambiguous or conflicting signals.
  Benefit: Estimated 10x reduction in LLM token spend.
  Evidence threshold: 0.80 (configurable in config.yaml).

DECISION 2: Evidence Cross-Check on DELETE Claims
  Problem: The activity log may show a DELETE event, but the record might still
           exist (failed deletion, sync recreated it, or backup restored it).
  Solution: After replaying DELETE events, check all EvidenceMatch records.
            If evidence shows the identifier still present → override to PRESENT.
  Rationale: "reported_status and operation success are claims, not proof."

DECISION 3: Historical Identifier Resolution
  Problem: User may have changed their email. Request may come from old email.
           Hash variants (MD5/SHA-256/SHA-1) may appear in evidence files.
  Solution: audit_log enriches the IdentityBundle with historical emails/names.
            All hash variants computed and included in all_identifiers set.
  Edge case: Email reassigned to different user → flag as ambiguous, resolve
             by timestamp to correct owner.

DECISION 4: Tombstone-Aware Gap Detection
  Problem: CRM tombstones are allowed to keep user_id but not PII.
  Solution: TOMBSTONE_FORBIDDEN = {name, email, phone, email_hash, ...}
            Evidence fields checked against this set.
            Any forbidden field found → EXPOSED_PII gap → must REDACT.

DECISION 5: Disk Cache for LLM + Evidence Text
  Problem: Multiple runs, multiple workers, same LLM prompts.
  Solution: SHA-256 content-addressable cache for LLM responses.
            Parsed text (PDF OCR, image OCR) also cached by filename.
  Benefit: Second run is essentially free for LLM calls.

DECISION 6: Per-Case Error Isolation
  Problem: One bad evidence file or unexpected schema should not kill all 518 cases.
  Solution: ThreadPoolExecutor catches per-case exceptions; logs them;
            emits INCOMPLETE + empty steps as safe fallback.

DECISION 7: Column Name Flexibility in rules.py
  Problem: Real CSVs may have slightly different column names.
  Solution: rules.py normalises all column names to lowercase and checks
            aliases (e.g., "action" OR "deletion_action" OR "treatment").

DECISION 8: Parallelism with Thread Safety Awareness
  Problem: ThreadPoolExecutor + shared JSONL log file.
  Note: llm_calls.jsonl uses open(..., "a") per call. In parallel, lines may
        interleave between workers but each json.dumps() call is atomic at the
        OS level for small payloads. Acceptable for competition context.

9. LLM STRATEGY
================================================================================

MODEL: claude-claude-sonnet-4-5 (configurable in config.yaml)

WHEN LLM IS CALLED:
  (a) Intent Stage-2:
      Trigger: regex confidence < 0.80 OR conflicting signals
      Prompt:  prompts/intent.txt — single-turn, strict JSON output
      Expected tokens: ~150 input, ~30 output
      Cache hit rate: ~100% after first run (same texts repeat)

  (b) Evidence extraction from unstructured text (PDF/image):
      Trigger: pdfplumber returns empty text (scanned PDF)
      Prompt:  prompts/evidence_extraction.txt — {{IDENTIFIERS}} + {{DOCUMENT_TEXT}}
      Expected tokens: varies by document length
      Cache: text result cached by filename to .cache/evidence/

  (c) Vision extraction from images:
      Trigger: pytesseract avg confidence < 60
      Prompt:  prompts/vision_extract.txt — {{IDENTIFIERS}}
      Method:  base64-encoded image sent to Anthropic vision API
      Output:  {"found": ["value1", ...]}

COST ESTIMATION (worst case, no cache):
  Intent LLM: ~200 cases ambiguous x 180 tokens = 36,000 tokens
  Evidence:   ~10 PDFs with OCR x 500 tokens = 5,000 tokens
  Total input tokens: ~41,000 (~$0.12 at $3/MTok)
  Total output tokens: ~15,000 (~$0.23 at $15/MTok)
  Estimated total cost: < $0.40 per full run

11. KNOWN LIMITATIONS & EDGE CASES
================================================================================

1. PDF FILES
   The evidence/ directory contains placeholder .pdf files (not real PDFs).
   Real competition PDFs will be handled by pdfplumber + pytesseract OCR.
   If OCR fails, vision LLM is invoked automatically.

2. RESOURCE_TYPE INFERENCE
   rules.py infers resource_type from system_id/resource_id name heuristics.
   Once real deletion_rules.csv columns are known, this can be exact-matched.
   Fallback: "record" type, treated as DELETE by default.

3. REASSIGNED EMAILS
   If an email was owned by user A until 2022-01-01 and then user B after,
   the agent resolves to the correct owner based on requested_at timestamp
   and logs an ambiguity warning. Both users' records are checked.

4. THREAD SAFETY OF JSONL LOG
   LLM call log uses open("a") — safe for single-threaded, but in multi-worker
   mode, log lines from different threads may interleave within a single write
   buffer. In practice, each line is small enough to be written atomically.

5. ACTIVITY LOG TIMESTAMP COLUMN
   state.py expects a "timestamp" column. If the real CSV uses a different name
   (e.g., "created_at", "event_time"), _filter_activity will not apply the time
   filter. Mitigation: load_data.py TIMESTAMP_COLS registry is updated with
   real column names once known.

6. NOT_APPLICABLE DEFAULT ON LLM FAILURE
   If the LLM fails (no API key, network error) and Stage-1 confidence < 0.80,
   the agent returns Stage-1 result with "[LLM unavailable]" in the reason.
   General conflicts default to is_deletion=False (safe/conservative).

7. BILLING/TAX RECORD PII
   Retained ORDER_MGMT/BILLING records are allowed to keep order_id and amount
   only. If evidence shows email or name in these records, an EXPOSED_PII gap
   is generated even though the record itself is retained.
